# API Feasibility Matrix

**As researched:** 2026-08-29. Every row below reflects the public macOS SDK and App Store Review Guidelines as of that date. Re-verify any row older than a year before acting on it — Apple adds and removes public API on a yearly OS cadence, and a "sandbox-blocked" or "impossible" verdict here is a snapshot, not a permanent law of the platform.

This document is the research record behind every API-dependent decision made elsewhere in `docs/`, so that no future contributor re-litigates a settled question. Each row names one capability NotchFlow needs, the mechanism that provides it, the minimum OS version, whether the mechanism is public or private, what entitlement it needs, whether it works inside the App Sandbox, whether it works in the Direct build, and a source. It is a design specification — nothing in this folder is code.

Four verdicts are used, and only these four:

- **Feasible with public API** — a documented Apple framework covers this, in the sandbox, with no unresolved risk.
- **Feasible only unsandboxed** — the mechanism works, but only outside the App Sandbox (private framework, or a private/undocumented system signal), so it is available to the Direct build only.
- **Sandbox-blocked** — a public mechanism exists but the App Sandbox's entitlement model refuses it outright; no entitlement unlocks it.
- **Impossible** — no public, private, or documented mechanism exists on macOS at all, in either build.

## Notes on the contested rows

**Row 10 — why `MediaRemote` cannot ship in the App Store build.** `MediaRemote.framework` has never had a public header, a documentation page, or an entitlement. Its symbols are reachable only by `dlopen`/`dlsym` against a private system framework, or by linking against reverse-engineered headers that the community maintains outside Apple's SDK. App Store Review Guideline 2.5.1 forbids exactly this: an app may not use non-public APIs, and static analysis of the submitted binary specifically checks for private-framework linkage and known private symbol names. This is a distribution-policy restriction, not a technical sandbox restriction — the framework is reachable from a sandboxed process on a developer's own Mac — but a submission that references it, sandboxed or not, is rejected on sight. That is why `10-build-and-distribution.md` routes music observation through two entirely different providers: `ScriptingBridge` for the App Store build, `MediaRemote` for the Direct build only, where private-API use has no reviewer to answer to.

**Row 15 — the honest state of microphone-in-use detection.** There is no single documented Apple API whose stated purpose is "tell me whether any process is currently using the microphone." What exists is the system-level orange-dot privacy indicator the OS itself draws in the menu bar, which is not exposed through a public, stable, sanctioned query method for third-party apps to read on other processes' behalf. The `AVFoundation` authorization APIs cited above govern *NotchFlow's own* microphone access, not a system-wide "is the mic in use" boolean. Any implementation of this provider that goes further than checking NotchFlow's own capture state is relying on an undocumented signal (for example, polling CoreAudio's running IO state, or the same private mechanism `MediaRemote` for now-playing rests on) and inherits the same App Store Review risk as row 10. Treat this row as **feasible only unsandboxed** and revisit it with the same distribution split as music: no proven public path exists for the App Store build, and the Direct build's implementation should be treated as best-effort and re-verified against actual observed behavior before being called reliable, since — unlike `MediaRemote` — no comprehensive reverse-engineering writeup for this exact signal is presently known to the author of this row.

**Row 16 — why AirDrop and generic transfer progress are not observable.** AirDrop's UI, queue, and progress state live entirely inside `sharingd` and the Finder/Share Sheet process. Apple has never published a framework, distributed notification, or IPC channel that exposes an AirDrop transfer's progress, source, or destination to a third-party process — sandboxed or not. The only public AirDrop-adjacent surface (`NSSharingService`) lets an app *initiate* an AirDrop send of its own content; it exposes no way to observe transfers already underway, whether initiated by NotchFlow or any other app. The same reasoning applies to third-party download progress in general: Safari, mail clients, and other download-capable apps do not publish a shared, observable "download in progress" signal, and each app's download manager is private implementation detail. Both capabilities are marked **impossible**, not merely sandbox-blocked, because no version of NotchFlow — App Store or Direct, sandboxed or not — has any documented path to this information.

**Row 18 — why incoming calls are impossible on macOS.** `CallKit` exists to let a *VoIP calling app* register itself with the system call UI; it has no counterpart API for a *third-party, non-telephony app* to observe another app's call state. FaceTime and the Phone Link (Android phone-mirroring) app do not publish call state through `MediaRemote`, a distributed notification, or an `NSWorkspace` event — there is no "a call is ringing" broadcast on macOS analogous to the now-playing broadcast music apps use. Building this would require either a private framework with no known public surface, or cooperation from Apple that does not exist today. It is tracked in `docs/13-deferred-backlog.md` with the trigger condition: revisit only if Apple ships a public, read-only call-state observation API.

**Row 19 — why `ActivityKit` does not apply.** `ActivityKit` (Live Activities) ships only for iOS, iPadOS, and watchOS; Apple's own platform-availability table for the framework does not list macOS, and no `ActivityKit` symbol is present in the macOS SDK. NotchFlow's "Activity" concept, defined in `05-activity-model.md`, is a same-named but entirely NotchFlow-owned Swift protocol with no relationship to Apple's framework of the same name — the naming overlap is coincidental and worth flagging so a future contributor does not go looking for an `ActivityKit` import that will never exist on this platform.

## Re-verification instruction

Every row above was checked against the SDK and App Store Review Guidelines current as of the date at the top of this document. Before relying on any row to justify a code change, confirm it is still less than one year old; if it is older, re-run the check against the current SDK and guidelines and update the date and the row before proceeding. macOS ships a major SDK revision every year, and both new public APIs and new review-guideline language can change a verdict in either direction.
