# API Feasibility Matrix

**As researched:** 2026-08-29. Every row below reflects the public macOS SDK as of that date. Re-verify any row older than a year before acting on it — Apple adds, removes, and restricts API on a yearly OS cadence, and a "private API" or "impossible" verdict here is a snapshot, not a permanent law of the platform.

This document is the research record behind every API-dependent decision made elsewhere in `docs/`, so that no future contributor re-litigates a settled question. Each row names one capability KerNotch needs, the mechanism that provides it, the minimum OS version, whether the mechanism is public or private, what entitlement it needs, whether it works in KerNotch's build — Developer ID signed, hardened runtime, not sandboxed (`10-build-and-distribution.md`) — and a source. It is a design specification — nothing in this folder is code.

Four verdicts are used, and only these four:

- **Feasible with public API** — a documented Apple framework covers this, with no unresolved risk.
- **Feasible with private or undocumented API** — the mechanism works in KerNotch, but rests on a private framework or an undocumented system signal that Apple can change or restrict in any release.
- **Feasible with third-party API** — the mechanism belongs to another vendor's app and works under that vendor's terms.
- **Impossible** — no public, private, or documented mechanism exists on macOS at all.

## Notes on the contested rows

**Row 10 — why `MediaRemote` is used only before macOS 15.4.** `MediaRemote.framework` has never had a public header, a documentation page, or an entitlement. Its symbols are reachable only by `dlopen`/`dlsym` against a private system framework, or by linking against reverse-engineered headers that the community maintains outside Apple's SDK. Apple owes it no stability, and has already used that freedom: from macOS 15.4 the framework returns now-playing metadata only to Apple-signed processes. KerNotch therefore runs its `MediaRemote` provider only on earlier releases, and uses `ScriptingBridge` (rows 11–13) for Spotify and Apple Music from 15.4 on. The branch that makes that choice, and the CI guards that keep both backends in the build, are specified in `06-activity-providers.md` and `10-build-and-distribution.md`.

**Row 15 — the honest state of microphone-in-use detection.** There is no single documented Apple API whose stated purpose is "tell me whether any process is currently using the microphone." What exists is the system-level orange-dot privacy indicator the OS itself draws in the menu bar, which is not exposed through a public, stable, sanctioned query method for third-party apps to read on other processes' behalf. The `AVFoundation` authorization APIs cited above govern *KerNotch's own* microphone access, not a system-wide "is the mic in use" boolean. Any implementation of this provider that goes further than checking KerNotch's own capture state is relying on an undocumented signal (for example, polling CoreAudio's running IO state, or the same private mechanism `MediaRemote` for now-playing rests on) and inherits the same instability as row 10. Treat this row as **feasible with private or undocumented API**: KerNotch's implementation should be treated as best-effort and re-verified against actual observed behavior before being called reliable, since — unlike `MediaRemote` — no comprehensive reverse-engineering writeup for this exact signal is presently known to the author of this row.

**Rows 24 and 25 — why finding an agent's editor depends on KerNotch not being sandboxed.** Both calls are public and unprivileged, and both return an empty result under the App Sandbox rather than an error: measured on macOS 26, an unsandboxed process saw 631 processes, 627 executable paths and 427 working directories, while the same binary inside a sandboxed bundle saw zero of each. A feature built on them inside the sandbox degrades into silently doing nothing, which is why they are safe to rely on only in an unsandboxed app like KerNotch. Row 26 is deliberately listed beside them: the *acting* half of "open the window the agent is running in" needs no process visibility, measured, so only the discovery depends on these calls.

**Row 16 — why AirDrop and generic transfer progress are not observable.** AirDrop's UI, queue, and progress state live entirely inside `sharingd` and the Finder/Share Sheet process. Apple has never published a framework, distributed notification, or IPC channel that exposes an AirDrop transfer's progress, source, or destination to a third-party process. The only public AirDrop-adjacent surface (`NSSharingService`) lets an app *initiate* an AirDrop send of its own content; it exposes no way to observe transfers already underway, whether initiated by KerNotch or any other app. The same reasoning applies to third-party download progress in general: Safari, mail clients, and other download-capable apps do not publish a shared, observable "download in progress" signal, and each app's download manager is private implementation detail. Both capabilities are marked **impossible** because no third-party process has any documented path to this information.

**Row 18 — why incoming calls are impossible on macOS.** `CallKit` exists to let a *VoIP calling app* register itself with the system call UI; it has no counterpart API for a *third-party, non-telephony app* to observe another app's call state. FaceTime and the Phone Link (Android phone-mirroring) app do not publish call state through `MediaRemote`, a distributed notification, or an `NSWorkspace` event — there is no "a call is ringing" broadcast on macOS analogous to the now-playing broadcast music apps use. Building this would require either a private framework with no known public surface, or cooperation from Apple that does not exist today. It is tracked in `docs/13-deferred-backlog.md` with the trigger condition: revisit only if Apple ships a public, read-only call-state observation API.

**Row 19 — why `ActivityKit` does not apply.** `ActivityKit` (Live Activities) ships only for iOS, iPadOS, and watchOS; Apple's own platform-availability table for the framework does not list macOS, and no `ActivityKit` symbol is present in the macOS SDK. KerNotch's "Activity" concept, defined in `05-activity-model.md`, is a same-named but entirely KerNotch-owned Swift protocol with no relationship to Apple's framework of the same name — the naming overlap is coincidental and worth flagging so a future contributor does not go looking for an `ActivityKit` import that will never exist on this platform.

## Re-verification instruction

Every row above was checked against the SDK current as of the date at the top of this document. Before relying on any row to justify a code change, confirm it is still less than one year old; if it is older, re-run the check against the current SDK and update the date and the row before proceeding. macOS ships a major SDK revision every year, and both new public APIs and new restrictions on existing ones — as macOS 15.4 imposed on row 10 — can change a verdict in either direction.
